# M2.4.1 — Controlled Catalog Import Design Freeze and Legacy Inventory

## 1. Executive conclusion

M2.4 can proceed without changing the committed catalog schema, lifecycle, supersession, immutability, or PostgreSQL concurrency contracts.

The current legacy source contains exactly 106 references, matching the historical regression count. The controlled inventory found:

- 3 `valid_candidate`;
- 103 `suspicious_candidate`;
- 0 `invalid_candidate`;
- 227 raw aliases, collapsing to 191 normalized aliases;
- no exact or normalized alias shared by different references;
- 90 records with `calories_per_100g`;
- 16 with `default_calories`;
- 95 without a declared source;
- 1 declared internal estimate;
- no structurally malformed record;
- no evidenced `FoodPortion`: all 106 `default_grams` values lack explicit unit/conversion provenance.

“Valid” means suitable for controlled draft staging, not approved nutritional truth. All imported entities must remain drafts under one global, untrusted `legacy_config` source. No resolver/runtime integration belongs to M2.4.

M2.4.1 is not declared approved by this report. The main remaining gate is implementation and PostgreSQL verification of the frozen design.

## 10. Confirmed incompatibilities or blockers

No committed schema, lifecycle, supersession, or concurrency incompatibility blocks the frozen import design.

Constraints that close unsafe paths:

- Initial creation cannot be routed through supersession services. A dedicated import application service must create initial source/reference/draft rows and explicit creation events.
- An untrusted legacy source intentionally prevents later activation eligibility. This is protection, not a defect.
- `default_grams` cannot safely produce any current `FoodPortion`.
- Post-commit deletion cannot be used as rollback because PostgreSQL triggers prohibit physical deletion. Recovery must use explicit lifecycle governance.
- Updating a deterministic identity with changed content is prohibited. It must be reported as a conflict, not silently synchronized.
- Adding an importer observer, automatic UUID boot hook, seeder, activation shortcut, or database importer trigger is a blocked path and would require a prerequisite correction phase.

Operational limitations found:

- Docker was stopped, so the current normalizer could not be executed through Sail. The inventory used a direct textual parser and a source-equivalent implementation of its inspected algorithm. This must be reconfirmed in focused Pest tests.
- Required M2.3.4 report files are currently untracked despite the stated “complete and committed” status. The committed implementation is present and coherent; report tracking is repository hygiene, not an import architecture blocker.

## 12. Proposed M2.4 subphase decomposition

### M2.4.2 — Manifest, classification, and identity contracts

Objective: implement pure import contracts and deterministic rules.

Scope: manifest schema/value objects, issue codes, classification enum/rules, canonical identity builder, UUIDv5 namespace, canonical serialization/fingerprints, focused unit tests.

Exclusions: config extraction, Artisan commands, Eloquent, database writes, lifecycle events, resolver/runtime.

Validation: focused Pest unit tests with fixtures held inside tests.

Completion: rules reproduce 3/103/0 and stable identity vectors without side effects.

Dependency: M2.4.1.

### M2.4.3 — Legacy extraction, normalization, and dry-run generation

Objective: extract the current PHP config into a deterministic manifest.

Scope: dedicated extractor, use of `NormalizeFoodText`, category/source ordinal capture, checksums, duplicate/collision analysis, dry-run command, console/JSON report.

Exclusions: database writes and catalog creation.

Validation: repeated generation produces byte-identical manifests; focused feature tests cover the 106-record inventory and issue counts.

Dependency: M2.4.2.

### M2.4.4 — Controlled draft application

Objective: atomically apply an approved manifest.

Scope: explicit import application service; deterministic source/reference/version/link/alias creation; draft state only; creation events; actor requirement; unchanged/conflict checks.

Exclusions: portions, approval/publication/activation, successor workflows, resolver/runtime.

## 14. Risks and explicit non-goals

### Risks

- “Valid” may be misunderstood as nutritionally verified; UI/report language must say “valid import candidate.”
- TACO strings can be mistaken for a verified TACO dataset.
- Draft suspicious records may later be activated without proper editorial correction if governance is bypassed.
- Preparation and generic identities require human concept decisions.
- Deterministic identity makes silent source changes visible as conflicts; operators must not “fix” this with upserts.
- Post-commit physical rollback is intentionally unavailable.
- Manifest approval depends on review of an exact checksum; a broader signed-approval system is outside M2.4.

### Non-goals

- no source verification;
- no schema redesign;
- no portion inference;
- no per-100g conversion from serving assumptions;
- no lifecycle redesign;
- no successor use for initial creation;
- no seeder;
- no generic import framework;
- no resolver implementation or runtime cutover;
- no meal/estimate changes;
- no LLM classification;
- no nutritional judgment from memory, RAG, embeddings, or history.
