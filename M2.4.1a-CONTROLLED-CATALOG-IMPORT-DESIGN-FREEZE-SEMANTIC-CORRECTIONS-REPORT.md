# M2.4.1a — Controlled Catalog Import Design Freeze Semantic Corrections

## 1. Corrected executive conclusion

**[Observed]** O inventário legado permanece válido: 106 referências, 3 `valid_candidate`, 103 `suspicious_candidate`, 0 `invalid_candidate`, 227 aliases brutos e 191 aliases normalizados. Nenhuma evidência do repositório alterou esses totais.

**[Observed]** A classificação não determina persistência. O manifesto precisa separar:

```text
candidate_classification
identity_resolution
selected_for_apply
```

**[Inherited]** `FoodSource` e `FoodReference` não possuem lifecycle draft. A fonte nasce `available`, com autoridade `untrusted`; a referência nasce `available`, com sua identidade imutável. Somente `FoodReferenceVersion` e `FoodAlias` entram em `review_status=draft`.

**[Recommended]** Mesmo os três candidatos válidos permanecem manifest-only enquanto `stable_key`, `is_generic`, `classification` e `preparation_key` não estiverem explicitamente resolvidos. Não existe, portanto, um total aprovado para aplicação nesta passagem.

**[Recommended]** O artefato legado será uma única fonte global `legacy_config`, sem coluna `code`. O identificador lógico `legacy_config_nutrition_v1` pertence a uma constante de aplicação, ao metadata da fonte e às entradas UUIDv5.

**[Inherited]** As operações exatas já comprometidas são:

- `create_source`;
- `create_reference`;
- `create_draft`.

**[Recommended]** A fonte legado será o vínculo `primary` da versão como evidência principal do valor importado, porém continuará `authority_status=untrusted`. Isso é compatível com a policy: submissão permite primary untrusted, enquanto ativação exige primary eligible. “Primary” é papel da evidência, não autoridade oficial.

M2.4 pode prosseguir sem migrations ou mudanças nos contratos comprometidos, mas o design original não deve ser implementado sem estas correções semânticas.

## 3. Complete immutable-field persistence eligibility rule

Cada registro do manifesto deve conter três blocos independentes:

```json
{
  "candidate_classification": "valid_candidate|suspicious_candidate|invalid_candidate",
  "identity_resolution": {
    "status": "resolved|unresolved|conflict",
    "issues": []
  },
  "selected_for_apply": false
}
```

### Regra de elegibilidade

**[Recommended]** `selected_for_apply=true` somente quando todas as condições forem satisfeitas:

1. `candidate_classification` não é `invalid_candidate`.
2. `identity_resolution.status=resolved`.
3. O checksum da fonte corresponde ao manifesto.
4. O manifesto canônico possui checksum humano aprovado.
5. A referência alvo está explicitamente resolvida como conceito novo source-neutral ou referência existente identificada por `stable_key`.
6. `FoodReference.visibility=global`.
7. `FoodReference.owner_user_id=null`.
8. `FoodReference.is_generic` é booleano explicitamente decidido.
9. `stable_key` é conceitual, source-neutral, não vazio e não conflitante.
10. `FoodReferenceVersion.locale` está explicitamente resolvido.
11. `classification` está explicitamente resolvida e não vazia.
12. `preparation_key` tem valor explícito ou decisão explícita de `null` por conceito preparation-neutral.
13. A referência existente, se houver, possui visibility, owner e `is_generic` compatíveis.
14. Referência existente com versões não recebe silenciosamente version 1 ou linha paralela.
15. Cada alias selecionado tem locale, kind e normalização resolvidos.
16. Nenhuma identidade UUID, stable key ou chave normalizada conflita com outro plano de persistência.
17. A seleção foi explicitamente aprovada no manifesto.

### Resultados obrigatórios

- **[Blocked]** `invalid_candidate` nunca pode ser selecionado.
- **[Recommended]** `valid_candidate + unresolved identity` permanece manifest-only.
- **[Recommended]** `suspicious_candidate + resolved identity` pode ser selecionado para staging draft, com todos os issue codes preservados.
- **[Blocked]** `stable_key`, `is_generic`, `classification` ou preparation não podem ser inferidos silenciosamente para liberar aplicação.
- **[Inherited]** `FoodSource` e `FoodReference` são imutáveis desde a criação nos campos de identidade.
- **[Inherited]** Version/Alias são editáveis enquanto draft, mas isso não autoriza criar uma referência conceitualmente errada.

## 6. Corrected import replay and lifecycle-event semantics

### Persisted graph replay

**[Recommended]** O importer primeiro compara o grafo semântico persistido contra o manifesto:

- source;
- references;
- versions;
- source links;
- aliases;
- states;
- canonical semantic fingerprints.

Creation actor IDs, internal IDs, database timestamps and event UUIDs do not participate in the semantic graph fingerprint.

If the complete graph is equal:

```text
import outcome = no_op
new entity rows = 0
new lifecycle events = 0
```

Isso permanece verdadeiro quando a segunda execução usa outro ator ou outro occurred-at. A primeira auditoria de criação permanece autoritativa.

If the graph is partial, mismatched or has the same deterministic identity with different content:

```text
import outcome = conflict
automatic repair = prohibited
new events = 0
```

### Lifecycle-event replay

**[Inherited]** Exact event replay requires the same:

- subject type and ID;
- operation;
- actor ID;
- actor reference;
- normalized reason;
- idempotency key;
- occurred-at instant.

A reused event key with a different command fingerprint remains `idempotency_key_reused`.

**[Blocked]** M2.4 must not change `CatalogLifecycleCommandFingerprint` or omit actor/time fields.

### Concurrent first application

**[Recommended]** The future apply service must:

1. obtain an importer-scoped PostgreSQL transaction lock;
2. recheck the complete graph under the lock;
3. let the winner create the graph and events;
4. make the loser observe the completed graph and return import no-op;
5. never let the loser append duplicate creation events.

### Different actor or occurred-at

- Graph already complete: import no-op, no lifecycle command constructed.
- Graph absent: the new actor/occurred-at produces a different lifecycle idempotency key and exact command fingerprint.
- Graph partial: conflict, not event replay.
- Same event key with different actor/time: inherited idempotency conflict.

### Atomicity labels

- **[Inherited]** Entity mutation and its lifecycle event are atomic.
- **[Recommended]** All selected graphs in one manifest use one outer transaction.
- **[Recommended]** Batch size 100 applies only to preflight/read grouping.
- **[Recommended]** Graph-level replay is an importer contract, not lifecycle replay.
- **[Inherited]** Event-store replay semantics and command fingerprint remain unchanged.

## 7. Corrected source/manifest checksum contract

Two hashes are mandatory and distinct.

### Source checksum

**[Observed]**

```text
artifact: config/nutrition.php
algorithm: sha256
sha256: 0d3987cc616b40e878731ecda0127a5b0a065f9557977b5b8f4ec0091d4ecc21
bytes: 25676
```

The manifest embeds this value in `source.sha256`.

### Manifest checksum

**[Recommended]** SHA-256 over the exact canonical UTF-8 manifest bytes. The checksum itself is outside the hashed payload or stored in an outer envelope to avoid self-reference.

The human-approved artifact is:

```text
canonical manifest + exact manifest SHA-256
```

The source hash remains an independently verified precondition.

### Commands

Dry-run generation:

```text
catalog:plan-legacy-import \
  --source=config/nutrition.php \
  --expected-source-sha256=<source-sha256> \
  --manifest-output=<path> \
  --report=<path-or-dash>
```

Apply:

```text
catalog:apply-legacy-import \
  --manifest=<path> \
  --expected-manifest-sha256=<manifest-sha256> \
  --expected-source-sha256=<source-sha256> \
  --actor=<user-id> \
  --occurred-at=<RFC3339-with-microseconds>
```

Apply verification order:

1. Hash canonical manifest bytes and compare with `--expected-manifest-sha256`.
2. Read manifest schema/version.
3. Hash raw source bytes.
4. Compare raw source hash with `--expected-source-sha256` and `manifest.source.sha256`.
5. Reject any mismatch before database mutation.
6. Run graph preflight and identity-resolution checks.
7. Apply only the exact human-approved selection.

**[Blocked]** `--expected-sha256` is removed from the design.

## 8. Corrected M2.4 subphase decomposition

### M2.4.2 — Manifest and semantic contracts

Scope:

- candidate classification;
- identity-resolution state;
- apply-selection state;
- issue codes;
- logical artifact descriptor;
- checksum value objects;
- fixed UUID namespace hierarchy and golden vectors;
- graph fingerprint contract.

No config extraction or persistence.

### M2.4.3 — Legacy extraction and candidate manifest

Scope:

- extract `config/nutrition.php`;
- use existing normalizer;
- reproduce verified inventory;
- produce classification and unresolved identity fields;
- generate deterministic candidate manifest.

No database writes and no automatic identity approval.

### M2.4.4 — Identity resolution and approved apply plan

Scope:

- source-neutral stable-key resolution;
- genericity, locale, classification, preparation, and alias-kind decisions;
- existing-reference lookup/preflight;
- `selected_for_apply`;
- exact manifest checksum approval.

No entity persistence.

### M2.4.5 — Controlled graph persistence

Scope:

- create fixed untrusted source;
- create only resolved references;
- create draft versions/aliases;
- primary untrusted evidence link;
- exact creation lifecycle operations;
- one outer transaction;
- graph replay/conflict handling.

No activation, portions, or runtime wiring.

### M2.4.6 — PostgreSQL concurrency and replay verification

Scope:

- concurrent first apply;
- same graph/different actor replay;
- changed graph conflict;
- event fingerprint preservation;
- partial failure rollback.

### M2.4.7 — Final controlled execution

Scope:

- regenerate source checksum;
- approve exact manifest checksum;
- final dry-run;
- apply selected records;
- replay to prove graph no-op;
- confirm source/reference available and version/alias draft;
- confirm zero published/active records.
