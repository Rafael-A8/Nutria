# M2.3.4.1 — Catalog Lifecycle and Immutability Design Freeze

Data da inspeção: 2026-07-12  
Commit inspecionado: `ad68934 Add nutrition catalog Eloquent persistence skeleton`

Legenda usada neste relatório:

- **[FATO CONFIRMADO]** comportamento ou estrutura comprovada no repositório ou pelo Laravel Boost.
- **[RECOMENDAÇÃO APROVADA]** decisão firme deste design freeze, pronta para implementação após as aprovações humanas listadas na seção 25.
- **[SUPOSIÇÃO]** premissa necessária que ainda não está codificada.
- **[PREOCUPAÇÃO ADIADA]** assunto deliberadamente fora de M2.3.4.
- **[APROVAÇÃO HUMANA NECESSÁRIA]** decisão de produto, governança, privacidade ou operação que não deve ser assumida silenciosamente.

## 1. Repository and Current Catalog Findings

### Repositório e ambiente

- **[FATO CONFIRMADO]** O catálogo persistido é composto pelas seis migrations `database/migrations/2026_07_11_191709_create_food_sources_table.php` até `database/migrations/2026_07_11_191745_create_food_portions_table.php` e pelos seis models em `app/Nutrition/Infrastructure/Catalog/Eloquent/`.
- **[FATO CONFIRMADO]** O PostgreSQL está acessível, porém `vendor/bin/sail artisan migrate:status` mostra as seis migrations do catálogo como `Pending`. Portanto, constraints e índices foram confirmados no código e nos testes comprometidos, não no schema atualmente migrado desse banco.
- **[FATO CONFIRMADO]** Laravel Boost reportou Laravel `13.13.0`, Pest `4.7.2`, PostgreSQL e PHP `8.5`; `AGENTS.md` ainda declara PHP `8.3`. O código futuro deve respeitar o constraint real do projeto e resolver essa divergência antes de CI/produção.
- **[FATO CONFIRMADO]** Não existe implementação produtiva de `DB::transaction()`, `lockForUpdate()`, lifecycle de catálogo, policy de autorização, trigger PostgreSQL ou histórico de eventos de catálogo.
- **[FATO CONFIRMADO]** `tests/Unit/Nutrition/Catalog/CatalogEloquentBoundaryTest.php` exige que lifecycle não seja colocado nos models e proíbe observers, hooks, global scopes e métodos como `activate`, `approve`, `publish`, `withdraw` e `supersede` neles.
- **[FATO CONFIRMADO]** O domínio novo usa enums e value objects `final readonly`, com resultados tipados e invariantes internas, especialmente `FoodResolution`. Essa é a convenção correta para M2.3.4, em vez dos arrays usados pelos services legados em `app/Services`.

### Schema atual

- **[FATO CONFIRMADO]** `FoodReferenceVersion`, `FoodAlias` e `FoodPortion` têm apenas `review_status` e um único conjunto de campos `submitted_*`, `reviewed_*`, `published_*`, `activated_*`, `deactivated_*`, `withdrawn_*` e `archived_*`.
- **[FATO CONFIRMADO]** Esses campos representam uma projeção do estado atual ou da última ocorrência. Eles não conseguem preservar várias submissões, retornos, ativações e desativações.
- **[FATO CONFIRMADO]** O schema já garante: um sucessor direto por predecessor; número único por referência/linhagem; uma versão ativa por referência; uma fonte primária por versão; uma chave ativa de alias por referência; e uma chave ativa de porção por referência.
- **[FATO CONFIRMADO]** Os predicados ativos são `activated_at IS NOT NULL AND deactivated_at IS NULL AND withdrawn_at IS NULL AND archived_at IS NULL`.
- **[FATO CONFIRMADO]** Checks PostgreSQL exigem aprovação e publicação antes da ativação. Para versões também exigem `energy_basis_grams > 0` e `energy_kcal > 0`.
- **[FATO CONFIRMADO]** SQLite recebe os partial unique indexes portáveis, mas não recebe os checks de vocabulário, ownership e lifecycle específicos do PostgreSQL.

### Conclusão principal

**[RECOMENDAÇÃO APROVADA]** Os campos atuais não são histórico de auditoria. M2.3.4 deve adicionar `catalog_lifecycle_events`, append-only e transacional, antes de implementar transições. Os campos atuais permanecem como projeção consultável do estado corrente. Essa decisão é indispensável para preservar ciclos como:

```text
draft → pending_review → draft → pending_review → approved
published_inactive → active → deactivated → active → deactivated
```

## 2. Lifecycle Vocabulary

### Estados derivados para Version, Alias e Portion

**[RECOMENDAÇÃO APROVADA]** Não adicionar uma segunda coluna de estado. O estado efetivo é derivado deterministicamente, nesta precedência: `archived`, `withdrawn`, `active`, `deactivated`, `published_inactive`, `rejected`, `approved`, `pending_review`, `draft`.

| Estado | Definição de projeção |
|---|---|
| `draft` | `review_status=draft`; sem publicação, withdrawal ou archive |
| `pending_review` | `review_status=pending_review`; conteúdo congelado |
| `approved` | `review_status=approved` e `published_at IS NULL` |
| `rejected` | `review_status=rejected`; terminal para a mesma linha |
| `published_inactive` | aprovado e publicado, mas não ativo e nunca/atualmente não deactivated |
| `active` | predicado ativo atual satisfeito |
| `deactivated` | publicado, `deactivated_at IS NOT NULL`, sem withdrawal/archive |
| `withdrawn` | `withdrawn_at IS NOT NULL`; terminal |
| `archived` | `archived_at IS NOT NULL`; terminal |

### Operações congeladas

- `create_draft`: cria identidade e conteúdo inicial.
- `edit_draft`: altera somente conteúdo editorial permitido em `draft`; não é transição de estado.
- `submit_for_review`: congela o conteúdo e cria evidência de submissão.
- `return_to_draft`: reviewer devolve conteúdo para edição, sempre com razão.
- `approve`: aceita o conteúdo; aprovação é o freeze permanente da linha.
- `reject`: rejeita a linha; terminal, exigindo nova versão/revisão para corrigir.
- `publish`: torna o conhecimento aprovado oficialmente publicável; irreversível.
- `activate`: habilita primeira utilização oficial.
- `reactivate`: reabilita conteúdo deactivated, após revalidação completa.
- `deactivate`: suspensão operacional reversível, sem negar a verdade histórica.
- `withdraw`: retirada emergencial/epistêmica terminal de conteúdo publicado.
- `archive`: encerramento terminal e não operacional.
- `create_successor`: cria nova versão/revisão draft, nunca altera conteúdo do predecessor.

**[RECOMENDAÇÃO APROVADA]** `FoodSource` usa `create`, `edit_while_unused`, `change_authority` e `archive`; não ganha review lifecycle simétrico. `FoodReference` usa somente `create_stable_identity` e `archive`; archive é terminal e restore é proibido.

## 3. FoodReferenceVersion Transition Matrix

Em todas as linhas bem-sucedidas: ator é obrigatório, `catalog_lifecycle_events.occurred_at` é obrigatório, a operação usa transação e o evento é gravado na mesma transação. `reason` é texto obrigatório onde indicado; `reason_code` é sempre obrigatório. `Idem` significa retry com a mesma idempotency key retorna o resultado original sem novo evento.

| Operação | Origem → destino | Ator / razão | Projeção e mutabilidade | Idem / terminal | Locks e pré-requisitos | Resultado/conflito |
|---|---|---|---|---|---|---|
| `create_draft` | inexistente → `draft` | author; razão opcional | cria IDs, versão e conteúdo; draft editável | Idem; não | parent reference; chave de idempotência; parent não archived; número reservado | `created`; `number_conflict`, `parent_archived` |
| `edit_draft` | `draft` → `draft` | author/editor; razão opcional | somente conteúdo draft; identidades, parent, número e supersession imutáveis | Não é no-op; não | row; não pode ter sucessor | `draft_updated`; `content_frozen` |
| `submit_for_review` | `draft` → `pending_review` | author/editor; razão opcional | seta `submitted_at/by`; limpa projeção anterior de review; conteúdo congela | Idem; não | row, parent, source links/sources | completeza, normalização, provenance e conceito válidos; `submitted` ou reason específico |
| `return_to_draft` | `pending_review` → `draft` | reviewer; razão obrigatória | limpa snapshot corrente de submission/review; evento preserva tudo; volta a editar | Idem; não | row | `returned_to_draft`; `invalid_transition` |
| `approve` | `pending_review` → `approved` | reviewer; razão obrigatória | seta `reviewed_at/by/reason`; conteúdo fica permanentemente imutável | Idem; não | row, parent | completeza ainda válida; self-approval proibida por policy | `approved`; `self_approval_prohibited` |
| `reject` | `pending_review` → `rejected` | reviewer; razão obrigatória | seta review fields; conteúdo não volta a editar | Idem; sim | row | `rejected`; `invalid_transition` |
| `publish` | `approved` → `published_inactive` | publisher; razão obrigatória no evento | seta `published_at/by`; conteúdo já estava imutável | Idem; irreversível | row, parent | parent não archived; `published`; `not_approved` |
| `activate` | `published_inactive` → `active` | activator; razão obrigatória | seta `activated_at/by`; conteúdo imutável | Idem; não | parent, row, active version, links, primary source | eligibility completa; `activated` ou reason de eligibility/concurrency |
| `reactivate` | `deactivated` → `active` | activator; razão obrigatória | novo `activated_at/by`; limpa snapshot de deactivation; eventos preservam ciclos | Idem; não | mesmos locks de activate | não superseded/withdrawn/archived; eligibility revalidada |
| `deactivate` | `active` → `deactivated` | operator; razão obrigatória | seta `deactivated_at/by/reason`; conteúdo intacto | Idem; não | parent, row | `deactivated`; `not_active` |
| `withdraw` | `published_inactive`, `active` ou `deactivated` → `withdrawn` | emergency editor; razão obrigatória | seta `withdrawn_at/by/reason`; permanece historicamente published | Idem; sim | parent, row | `withdrawn`; `not_published`, terminal conflicts |
| `archive` | `draft`, `approved`, `published_inactive`, `deactivated` ou `rejected` → `archived` | archivist; razão obrigatória | seta archive fields; conteúdo intacto | Idem; sim | parent, row | active deve ser deactivated antes; withdrawn não muda para archive |
| `create_successor` | predecessor aprovado/publicado/deactivated/withdrawn → predecessor inalterado + novo `draft` | author/editor; razão obrigatória | novo row; `supersedes_*` atribuído na criação e imutável | Idem; predecessor terminal somente se já era | parent, predecessor, head, active row | mesmo parent, conceito, `max+1`, predecessor sem successor |

**[RECOMENDAÇÃO APROVADA]** A aprovação não pode ser revogada. Conteúdo aprovado não retorna a draft. Publicado inactive não retorna a draft. Rejected, withdrawn e archived nunca retornam. Reactivation é permitida somente para suspensão operacional e sempre cria novo evento.

## 6. FoodSource and FoodReference Lifecycle

### FoodSource

| Operação | Origem → destino | Regras firmes |
|---|---|---|
| `create` | inexistente → usable/untrusted/prohibited | ator obrigatório; default `prohibited`; identidade, visibility, owner e kind imutáveis após criação |
| `edit_while_unused` | não archived/sem qualquer link → mesmo estado | citation, edition, checksum, URI e metadata editáveis; lock source e confirmar zero links |
| `change_authority` | não archived → novo authority status | governança explícita, ator e razão obrigatórios; pode ocorrer depois do uso e gera evento; não altera fatos publicados |
| `archive` | não archived → archived | terminal, razão obrigatória; proíbe novas ativações/reativações, mas não remove links históricos |

**[RECOMENDAÇÃO APROVADA]** Authority downgrade e source archive não desativam automaticamente conhecimento ativo; disparam alerta operacional e bloqueiam nova ativação. Retirada do conhecimento exige `deactivate` ou `withdraw` explícito e auditável.

### FoodReference

| Operação | Origem → destino | Regras firmes |
|---|---|---|
| `create_stable_identity` | inexistente → available | `public_id`, `stable_key`, visibility, owner e `is_generic` imutáveis desde a criação |
| `archive` | available → archived | terminal, sem restore; ator/razão obrigatórios; exige inexistência de versão, alias ou porção ativa |

**[RECOMENDAÇÃO APROVADA]** Ownership e visibility nunca mudam. Promoção private→global cria nova referência global editorialmente revisada, com provenance explícito; não converte a referência privada.

## 8. Review and Publication Semantics

- **[RECOMENDAÇÃO APROVADA]** Submission exige todos os campos obrigatórios, texto normalizado persistido, locale, conceito compatível, provenance estrutural e source links coerentes. Activation-only checks podem aguardar ativação, mas ausência de evidence essencial impede submission.
- **[RECOMENDAÇÃO APROVADA]** `pending_review` congela conteúdo. O reviewer pode somente aprovar, rejeitar ou retornar a draft.
- **[RECOMENDAÇÃO APROVADA]** Retornar a draft limpa os campos-projeção que deixaram de representar o estado atual. O evento append-only preserva ator, razão, timestamps e os estados anterior/próximo.
- **[RECOMENDAÇÃO APROVADA]** A mesma linha pode ser submetida várias vezes após retornos a draft. Cada submissão é um novo evento.
- **[RECOMENDAÇÃO APROVADA]** Rejeição é terminal. Uma correção rejeitada gera nova versão/revisão, sem editar a rejeitada.
- **[RECOMENDAÇÃO APROVADA]** Aprovação exige razão e congela permanentemente o conteúdo, mesmo antes da publicação. Aprovação não é revogável.
- **[RECOMENDAÇÃO APROVADA]** Self-approval é proibida por Laravel policy; o lifecycle service também exige evidência de que author e reviewer não são o mesmo ID, como defesa de integridade.
- **[RECOMENDAÇÃO APROVADA]** Publication significa disponibilização oficial imutável; activation significa elegibilidade corrente para resolver/calcular. Um published row pode permanecer inactive.
- **[RECOMENDAÇÃO APROVADA]** Publication é irreversível e ocorre uma vez. Withdrawal não apaga `published_at`; o item permanece historicamente published.
- **[RECOMENDAÇÃO APROVADA]** Depois da aprovação, somente campos de lifecycle-control podem mudar.

## 10. Source Authority and Ownership Rules

| Referência/conhecimento | Fonte | Decisão |
|---|---|---|
| global | global eligible | permitida |
| global | qualquer private | proibida |
| private owner A | global eligible | permitida |
| private owner A | private owner A eligible | permitida |
| private owner A | private owner B | proibida, sem revelar detalhes da fonte |
| qualquer | untrusted | pode permanecer draft/supporting evidence; nunca suporta activation como fonte obrigatória |
| qualquer | prohibited | não suporta submission/activation; vínculo legado só para provenance histórica |
| qualquer | `app_generated_estimate` | nunca suporta catalog activation, mesmo se authority for erroneamente `eligible` |

- **[RECOMENDAÇÃO APROVADA]** Um source archived continua ligado a conhecimento já usado para reproduzir história, mas não permite nova activation/reactivation.
- **[RECOMENDAÇÃO APROVADA]** Archive ou authority downgrade não desativa automaticamente; gera alerta e bloqueia novas ativações. Withdrawal/deactivation é decisão explícita.
- **[RECOMENDAÇÃO APROVADA]** Authority pode ser rebaixada depois de uso. Upgrade para `eligible` exige operação governada, reason e actor; não reativa conhecimento automaticamente.
- **[RECOMENDAÇÃO APROVADA]** Conteúdo/citation/checksum do source fica imutável após qualquer vínculo submetido; correção cria novo `FoodSource`.

## 11. Generic Alias Governance

**[RECOMENDAÇÃO APROVADA]** M2.3.4.2 introduz `AliasKind` com os valores exatos:

```text
common
generic
regional
brand
```

- `generic`: termo deliberadamente não específico; somente ativa em `FoodReference::is_generic=true`.
- `common`: nome comum específico ou neutro; pode apontar para reference generic ou específica, sujeito a review.
- `regional`: variante regional específica; segue a mesma compatibilidade de `common`.
- `brand`: marca/produto específico; não ativa em generic reference.

**[RECOMENDAÇÃO APROVADA]** Um alias `generic` pode existir como draft em reference específica para permitir correção editorial, mas submission e activation falham com `generic_alias_reference_mismatch`. Um alias específico pode apontar para generic reference apenas se `common` e review documentar que o nome ainda representa o conceito genérico; `brand` nunca pode. Não há fuzzy, substring ou longest-alias semantics.

**[FATO CONFIRMADO]** O schema atual usa `alias_kind varchar(16)` sem check e a factory usa `common`; o enum é compatível sem migration imediata. O check PostgreSQL do vocabulário deve entrar em M2.3.4.5 ou em migration própria aprovada antes dele.

## 12. Concept Identity Compatibility

**[RECOMENDAÇÃO APROVADA]** O schema é suficiente se `FoodReference.stable_key` for formalmente congelado como a chave do conceito estável, e não apenas um slug. Não adicionar `concept_key` duplicado.

Na criação de successor, o service deve exigir:

- mesmo `food_reference_id` e, portanto, mesmo `stable_key` e `is_generic` imutáveis;
- `classification`, `preparation_key` e `locale` iguais ao predecessor aceito;
- canonical name pode mudar apenas como correção linguística, sem mudar o conceito;
- source record pode mudar como nova evidence, sem redefinir identidade.

Assim, `raw tilapia → fried tilapia` falha por `preparation_key` e exige nova `FoodReference`. `tilapia → salmon` falha em review por incompatibilidade com `stable_key`; essa verificação semântica é editorial, pois não pode ser inferida confiavelmente apenas por banco.

**[APROVAÇÃO HUMANA NECESSÁRIA]** Confirmar que `stable_key` é a autoridade de identidade conceitual e que locale/preparation/classification não variam dentro da referência. Essa confirmação bloqueia M2.3.4.6, não os contratos básicos de M2.3.4.2.

## 13. Supersession Rules

- `supersedes_*_id` é atribuído somente na criação do successor e é imutável.
- Version predecessor pertence à mesma `FoodReference`; alias/portion predecessor pertence à mesma referência e à mesma `lineage_id`.
- Número é estritamente contíguo: novo número = head atual + 1. Gaps são proibidos.
- O predecessor deve ser o head atual e não pode já ter successor. Os unique indexes/FKs existentes são backstop, não substituem locks.
- Um row tem no máximo um successor direto, já garantido pelos unique atuais.
- Supersession nunca é declarada depois da criação e nunca modifica conteúdo publicado.
- Criar successor não desativa predecessor. Activation do successor substitui atomicamente o active row conflitante.
- Predecessor withdrawn pode ser superseded para correção, mas nunca reativado.
- Corridas retornam `successor_exists`, `number_conflict` ou `concurrency_conflict`, nunca mensagem crua do PostgreSQL.

## 14. Transaction and Locking Plan

### Ordem global de locks

1. Evento existente pela idempotency key, se houver.
2. Parent `food_references` por ID crescente.
3. Subject, predecessor e lineage head por tabela e ID crescente.
4. `food_reference_version_sources` por ID crescente.
5. `food_sources` por ID crescente.
6. Active/conflicting rows por ID crescente.
7. Inserção do evento e atualização da projeção.

Todo critical write usa `DB::transaction(..., attempts: 3)` e `lockForUpdate()`. Unique/check constraints continuam sendo backstop final. Nunca fazer preflight fora da transação.

### Pseudocódigo congelado

```text
submit(subject, command):
  transaction:
    replay = lock event by idempotency_key; return replay if found
    lock subject; lock parent; lock required sources in global order
    decision = entityPolicy.submit(snapshot, facts, command)
    return deterministic result if denied
    update projection to pending_review without changing content
    insert successful append-only event

approve/publish(subject, command):
  transaction:
    replay check; lock parent then subject
    evaluate exact source state and authorization boundary
    update only review or publication projection
    insert event in same transaction

activate first version(subject, command):
  transaction:
    replay check; lock parent, subject, source links, sources
    lock any active version for parent
    validate full eligibility
    if another active exists: conflict
    set activated projection; insert event

replace active version(successor, command):
  transaction:
    replay check; lock parent, successor/predecessor/head sorted
    lock source links/sources; lock active version
    validate successor and exact supersession chain
    deactivate current active with event
    activate successor with event; same correlation_id/transaction_id

activate alias/portion revision(subject, command):
  transaction:
    replay; lock parent, subject, predecessor/head, source
    lock rows matching active unique predicate
    validate evidence, scope and generic/preparation rules
    deactivate prior lineage/conflicting revision when replacement is explicit
    activate subject; append correlated events

deactivate/withdraw(subject, command):
  transaction:
    replay; lock parent then subject
    validate exact current state
    update only matching lifecycle group; append event

create successor(predecessor, command):
  transaction:
    replay; lock parent, predecessor and lineage/reference head
    assert predecessor is head and has no successor
    next_number = head.number + 1
    insert new draft with immutable supersedes ID and copied identity fields
    append create_successor event
```

## 15. Idempotency and Conflict Semantics

- Toda write command exige UUID `idempotency_key`; a mesma key retorna exatamente o resultado original.
- Uma key reutilizada com payload/subject/operação diferente retorna `idempotency_key_reused`.
- Com nova key, alcançar um estado já alcançado por `approve`, `publish`, `activate`, `deactivate`, `withdraw` ou `archive` retorna no-op success `already_*`, sem sobrescrever actor/reason e sem novo state-change event. Um command-attempt event pode registrar a tentativa.
- Repetir `submit_for_review` enquanto já pending retorna no-op `already_pending_review`; submeter novamente após retorno a draft cria novo evento real.
- Aprovar estado não pending, publicar não approved ou ativar não published são `invalid_transition`.
- Tentar ativar predecessor superseded é `superseded_predecessor`.
- Duas successor activations concorrentes: uma vence; a outra retorna `active_version_conflict` após reler o estado sob lock/unique violation traduzida.

Reason codes compartilhados mínimos:

```text
transition_applied, already_pending_review, already_approved, already_published,
already_active, already_deactivated, already_withdrawn, already_archived,
invalid_transition, terminal_rejected, terminal_withdrawn, terminal_archived,
idempotency_key_reused, actor_required, reason_required, incomplete_content,
not_found, unauthorized, concurrency_conflict, catalog_integrity_violation,
persistence_failure
```

Texto humano fica fora do domínio e é resolvido pela camada de apresentação/tradução.

## 16. Lifecycle Result and Exception Design

**[RECOMENDAÇÃO APROVADA]** Usar estratégia mista mínima:

- `CatalogLifecycleResult`, `final readonly`, para outcomes esperados: `succeeded`, `no_op`, `invalid_transition`, `validation_failed`, `conflict`.
- `CatalogLifecycleReason` enum para reason code estável.
- `CatalogEligibilityResult`, `final readonly`, para lista ordenada de falhas de eligibility.
- Not found e unauthorized são checados na application boundary e convertidos em `not_found`/`unauthorized` sem revelar private data; controllers/policies podem lançar as exceções Laravel apropriadas.
- Violação conhecida de unique/check é capturada e traduzida para conflito/integrity reason.
- Falha de infraestrutura inesperada lança `CatalogPersistenceException`, com exception original encadeada e reportada; nunca expõe mensagem SQL como semântica de lifecycle.
- Boolean e arrays mistos são proibidos.

## 18. Audit-History Decision

**[RECOMENDAÇÃO APROVADA — OPÇÃO B]** Adicionar uma tabela única `catalog_lifecycle_events`, append-only. Opção A é rejeitada porque campos singulares não reconstroem ciclos. Opção C é rejeitada porque repete schema e consultas sem benefício proporcional.

Schema conceitual:

| Campo | Decisão |
|---|---|
| `id`, `public_id` | bigint interno + UUIDv7 público único |
| `subject_type` | enum lógico: source, reference, version, alias, portion |
| `subject_id`, `subject_public_id` | identidade interna e pública preservadas; associação polimórfica sem cascade delete |
| `event_type` | operação lifecycle estável |
| `outcome` | succeeded, no_op, invalid, validation_failed, conflict |
| `previous_state`, `next_state` | nullable para command attempts; obrigatórios em state changes |
| `actor_user_id` | ator auditável; recomendação `restrictOnDelete` |
| `reason_code`, `reason` | código estável + justificativa editorial |
| `metadata` | JSONB estruturado, versionado, sem texto de UI |
| `occurred_at` | `timestampTz(6)`, definido pelo serviço |
| `idempotency_key` | UUID único por command; replay seguro |
| `correlation_id` | agrupa operação composta |
| `transaction_id` | UUID comum aos eventos da mesma transação |
| timestamps Laravel | somente `created_at`; sem `updated_at` semântico |

Regras:

- Evento bem-sucedido e projeção são gravados atomicamente.
- Falhas/conflitos ocorridos antes de mutation podem ser registrados em transação independente como command attempts; nunca fingem state change.
- Update/delete são proibidos por grants e trigger PostgreSQL; retenção é permanente.
- Replays idempotentes retornam o evento original; não criam duplicata.
- Supersession gera evento no successor e metadata com predecessor; replace active gera eventos correlacionados de deactivate/activate.
- M2.3.4.3 é dona da migration, model, writer contract e testes append-only.

## 19. PostgreSQL Immutability Trigger Design

| Tabela | Trigger | Proteção |
|---|---|---|
| `food_sources` | `trg_food_sources_guard_immutable` BEFORE UPDATE/DELETE | identidade sempre; conteúdo depois de uso; somente authority/archive groups permitidos |
| `food_references` | `trg_food_references_guard_immutable` BEFORE UPDATE/DELETE | todos os campos estáveis; somente archive group permitido |
| `food_reference_versions` | `trg_food_reference_versions_guard_immutable` BEFORE UPDATE/DELETE | identidade sempre; conteúdo bloqueado enquanto pending e permanentemente desde approval; lifecycle groups permitidos |
| `food_reference_version_sources` | `trg_food_reference_version_sources_guard_immutable` BEFORE INSERT/UPDATE/DELETE | alteração somente se parent draft; congelado de pending em diante |
| `food_aliases` | `trg_food_aliases_guard_immutable` BEFORE UPDATE/DELETE | mesma regra de version |
| `food_portions` | `trg_food_portions_guard_immutable` BEFORE UPDATE/DELETE | mesma regra de version |
| `catalog_lifecycle_events` | `trg_catalog_lifecycle_events_append_only` BEFORE UPDATE/DELETE | rejeita toda mutation/delete |

**[RECOMENDAÇÃO APROVADA]** Freeze PostgreSQL começa em `pending_review` enquanto o row permanece pending. `return_to_draft` pode alterar apenas lifecycle fields; conteúdo só pode mudar em update posterior já draft. Desde `approved`, freeze é permanente. Publication não muda o freeze point.

As funções usam `IS DISTINCT FROM` por coluna, validam que timestamp/actor/reason mudam como grupo coerente e lançam SQLSTATE próprio documentado. Application services traduzem SQLSTATE para `catalog_integrity_violation`; raw exception não chega ao usuário. `down()` remove triggers antes das functions. Migrations antigas não são editadas.

## 20. SQLite and PostgreSQL Test Strategy

- Unit puro: enums, result shapes, transition policies, terminal states, reason mapping; sem Laravel DB.
- SQLite portable: application service happy paths, validation, append-only writer via aplicação, idempotency sequencial e projeção de estado.
- PostgreSQL integration: todos os checks, partial indexes, direct-SQL bypass, trigger content freeze, lifecycle-group coupling e event append-only.
- PostgreSQL concurrency: successor creation, dual activation, active replacement, idempotency race e deadlock/retry.
- Trigger-specific: UPDATE/DELETE direto contra cada tabela, alteração de source links após pending, retorno a draft sem content mutation.
- SQLite não testa `lockForUpdate` real, SQLSTATE, trigger PL/pgSQL nem concorrência. Essas garantias não serão enfraquecidas para obter paridade.
- Os testes atuais de partial indexes permanecem. `CatalogPersistenceSqliteCompatibilityTest.php` continua limitado ao contrato portátil.

## 21. Authorization Boundary

- Laravel policies/controllers verificam permissão para review, approve, publish, activate, withdraw, archive e acesso ao owner scope antes do service.
- Lifecycle command sempre carrega actor ID para auditoria; domínio nunca busca `auth()`.
- Service valida ownership compatibility e não aceita actor ausente, mesmo se controller falhar.
- Self-approval é negada pela policy e novamente pela integridade do service.
- Não revelar existência de private subject/source de outro owner; retornar `not_found` ou `source_scope_mismatch` sanitizado.
- M2.3.4 não cria UI/controllers. Policies Laravel ficam adiadas até existir entry point, mas o contrato exige autorização previamente confirmada.

## 22. Archive and Deletion Policy

- Nenhuma catalog row é fisicamente deletada depois da criação, inclusive unused draft. Erros criam archive/rejected evidence; isso maximiza auditabilidade.
- Archive é terminal e exige razão.
- Reference não pode ser archived com version, alias ou portion active; primeiro deactivate/withdraw em transação explícita.
- Source pode ser archived enquanto conhecimento ativo o referencia, preservando história; bloqueia novas ativações e gera alerta.
- Owner private usa `restrictOnDelete`, como já ocorre. Actor history também deve ser preservada; recomendação `restrictOnDelete` em events.
- Archived/withdrawn content continua resolvível por ID para reproduzir estimativas históricas, mas nunca entra em novos cálculos oficiais.
- Resolver futuro deve consultar somente active predicate, sem global scope oculto nos models.
